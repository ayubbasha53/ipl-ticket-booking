# Seam Tickets: demo T20 cricket ticket booking (MERN + TypeScript)

An **independent demo project**. It is not affiliated with, endorsed by or authorised by the IPL or BCCI.
Team names are public franchise names; every fixture, squad, price and ticket is **sample (DEMO) data**.
Tickets generated by this app are never valid for stadium entry, and payments will run in sandbox mode.

## Prerequisites
Node 20+, npm 10+, and MongoDB. Easiest: Docker (the compose file starts a single-node replica set so transactions work in later phases).

## Run locally
```bash
npm install
cp .env.example .env            # then edit JWT_SECRET (see comment in the file)
npm run db:up                   # MongoDB replica set via Docker (skip if you have your own MongoDB)
# optional: create a dev admin. Set ADMIN_SEED_EMAIL, ADMIN_SEED_PHONE (+E.164) and ADMIN_SEED_PASSWORD in .env first
npm run seed
npm run dev                     # API on :4000, web on http://localhost:5173
```
The Vite dev server proxies `/api` to the API, so cookies are same-origin.

**Email in development:** with `EMAIL_PROVIDER=console` nothing is delivered. The API prints a warning that includes the verification/reset link so you can complete the flows. For real delivery use `EMAIL_PROVIDER=brevo` with `BREVO_API_KEY` (HTTPS API; works on hosts that block SMTP ports, such as Render's free tier), or `EMAIL_PROVIDER=smtp` with `SMTP_*` where SMTP ports are open. Production refuses to start in console mode.

### Tests
Server integration tests use `mongodb-memory-server`, which downloads a `mongod` binary on first run. If your network blocks that download, point it at a local binary:
```bash
MONGOMS_SYSTEM_BINARY=/path/to/mongod npm test -w server
```

## Security notes (implemented in Phase 2)
- Passwords hashed with bcrypt (cost 12). Reset and verification tokens are random, stored only as SHA-256 hashes, expire, and are consumed atomically (single use).
- Sessions: JWT in an **httpOnly, SameSite=Lax** cookie, backed by a server-side session record so logout and password changes revoke immediately. Nothing sensitive is in localStorage.
- CSRF: double-submit cookie plus Origin check. Zod validates every body (also blocks NoSQL operator objects). Helmet, CORS allow-list, rate limits on auth routes, per-account lockout after 5 failures, constant-time-ish unknown-account handling, generic responses on forgot-password and resend.
- Audit log entries for register, login success/failure, resets and password changes. Logs never contain passwords or tokens (demo-mode email link is printed only outside production).

## Production notes
Set `NODE_ENV=production`, `COOKIE_SECURE=true`, a strong `JWT_SECRET`, a real `EMAIL_PROVIDER=smtp`, and a replica-set `MONGODB_URI`. Serve the client build from HTTPS on the same site as the API (or configure the proxy so cookies stay first-party) and set `CLIENT_URL` to that origin. Full deployment guide comes with Phase 9.

## Troubleshooting
| Symptom | Fix |
|---|---|
| `Invalid environment configuration` on start | Read the listed variables; copy `.env.example` to `.env` and fill `JWT_SECRET` (32+ chars) |
| `MongooseServerSelectionError` | MongoDB is not running. `npm run db:up`, or fix `MONGODB_URI` |
| 403 "Security check failed" | Cookies blocked, or the web app is not using the Vite proxy / same origin as `CLIENT_URL` |
| No verification email | You are in console demo mode. Use the link printed by the API, or configure SMTP |
| Tests cannot download MongoDB | Use `MONGOMS_SYSTEM_BINARY` as shown above |
